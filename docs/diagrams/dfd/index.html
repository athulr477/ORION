Process 0.0: Orion Governance Engine — External System Boundary Interactions

Description for Report Chapter 3

Figure 3.1 illustrates the Context Level (Level 0) DFD for the Orion Automated Traceability Engine. The central process 0.0 Orion Governance Engine interfaces with four primary external entities (Jira Cloud, GitHub CI/CD, Developer, and QA Lead / Auditor) as well as the central PostgreSQL (pgvector) database store.

  • Jira Cloud: Transmits issue webhooks with ADF descriptions; receives automated traceability status comments and sync badges.
  • GitHub CI/CD: Delivers pull request commit diffs and test files; receives pass/fail verification check run statuses that gate pull request merges.
  • Developer: Authors test cases and code commits; receives XAI diagnostic feedback and gap explanations for unresolved requirements.
  • QA Lead / Auditor: Defines sensitivity thresholds (τsem, τstruct), performs manual overrides, and audits compliance via the real-time RTM dashboard.
  • PostgreSQL Database (orion_db): Stores high-dimensional 384-d requirement and test embeddings, the dynamic traceability matrix, and append-only audit trail logs.

Figure 3.2: Level 1 System Data Flow Diagram (Functional Decomposition)

Decomposition of Orion into 5 Core Subsystems and 4 Data Stores

Open Full SVG Download SVG

Description for Report Chapter 3

Figure 3.2 decomposes Process 0.0 into five modular subsystems (1.0 through 5.0) and four persistent data stores (D1 through D4):

  • 1.0 Requirements Ingestion: Ingests Jira ADF payloads, parses descriptions into clean text, generates 384-dimensional embeddings, and writes to D1: requirements.
  • 2.0 AST Test Extraction: Filters pull request diffs for Python test files, parses function nodes and assert statements, generates embeddings, and writes to D2: test_cases.
  • 3.0 Hybrid Risk Engine: Evaluates requirement-test pairs using a convex combination of cosine semantic similarity and AST structural overlap, storing verdicts in D3: trace_links.
  • 4.0 XAI Verbalization: Extracts gap evidence from unlinked or borderline requirements and invokes a local Ollama Llama 3.1:8b model to produce natural language audit rationales stored in D4: audit_logs.
  • 5.0 Gating & Visualization: Emits GitHub Check Run conclusions, posts Jira comments, and provides a real-time React RTM matrix with RBAC-controlled override controls.

Figure 3.5: Level 2 DFD — Subsystem 3.0 (Hybrid Risk Engine)

Detailed Data Flow: Cosine Distance Matcher, AST Structural Overlap, Convex Fusion & Classification

Open Full SVG Download SVG

Description for Report Chapter 3

Figure 3.5 demonstrates the dual-scoring traceability computation of Subsystem 3.0:

  • 3.1 Cosine Distance Matcher: Computes the semantic similarity score Ssem = cos(θ) between requirement and test embedding vectors via pgvector.
  • 3.2 AST Structural Matcher: Calculates keyword token and entity overlap Sstruct between requirement constraints and extracted test assertion operands.
  • 3.3 Convex Combination: Synthesizes the hybrid confidence metric: Shybrid = 0.6 · Ssem + 0.4 · Sstruct.
  • 3.4 Threshold Classifier: Classifies the link as PASS (if both thresholds τsem and τstruct are satisfied), REVIEW, or FAIL, and updates D3: trace_links.

Figure 3.6 illustrates the verification closure loop. Process 4.1 (Evidence Diff Packager) gathers requirement text, matched AST nodes, and similarity differentials.
